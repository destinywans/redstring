# V3 alert-group bulk actions

`POST /api/v1/alert-groups/bulk` accepts a JSON object with `ids` (1–20 unique `group:` IDs, each followed by 24 lowercase hex characters) and `action` (`claim`, `investigate`, or `silence`). A write requires one selected environment. The group ID uses the same persisted environment key, application ID, and alert title as `GET /alert-groups`; it is a derived identity, not a client-supplied incident ID. The handler must resolve current members from storage, lock them, and apply current application or owner-team authorization for each group.

The response preserves input order and has one result per requested ID: `{id,outcome,matched,changed,investigation_id,proposal_id,error}`. IDs and error are `null` when they do not apply. `matched` counts persisted members in a bounded, authorized group and is zero when the group is hidden, missing, or too large to count safely; `changed` counts incident rows changed and is zero for a pending silence proposal. `200` means every item succeeded. `207` means at least one item failed, so callers must inspect every result. A missing or hidden group returns `not_found`; routine group conflicts and disconnected sources appear in the corresponding item. An invalid batch, an aggregate environment, or unavailable shared storage or policy fails the request before item results.

| Action | Successful outcome | Durable effect and retry |
| --- | --- | --- |
| `claim` | `claimed`, `already_claimed` | Set the platform assignee on eligible persisted members; the same user's retry does not add another change. It does not change Alertmanager state or notification delivery. |
| `investigate` | `investigating`, `already_investigating` | Create or reuse a real investigation and root branch linked to the locked group snapshot. Return only a persisted investigation ID. |
| `silence` | `pending_approval` | Create or reuse a pending proposal for the exact configured Alertmanager scope of an existing open linked investigation. Return the persisted proposal ID. This is an approval request, not an active silence. |

Silence additionally requires the operator-attested V3 alert-range coverage from the oldest active member through the request time, a single current inbound mapping that fixes the same `application`, environment, and `alertname` labels as the outbound Alertmanager binding, and active members from that one authenticated source. The ingress environment label must equal the proposal ledger's label. Synthetic patrol alerts, absent coverage history, mixed sources, ambiguous mappings, or label disagreement return `not_connected`. The legacy incident table does not retain raw webhook labels; this gate relies on current server configuration and the operator's historical coverage assertion. A matching incident inserted after the locked snapshot may join the derived group before proposal review. Approval and independent execution must revalidate source, group membership, and scope before any upstream silence.

Item failures include `not_found`, `conflict`, `not_connected`, `investigation_required`, `group_too_large`, `session_revoked`, `human_required`, and `unavailable`. `not_connected` identifies missing configured source or exact Alertmanager scope; `investigation_required` asks for a linked open investigation before a silence proposal. Investigate also requires the current `canvas.change` grant. No direct upstream silence, infrastructure write, or external notification occurs in this handler. V3 approval and independent execution are separate, as yet unwired paths; a `pending_approval` result must never be displayed as “silenced.”

The standalone contract fragment is [`scripts/v3-openapi-alert-groups-bulk.py`](../../scripts/v3-openapi-alert-groups-bulk.py). The frozen frontend currently sends unsupported `merge` and `assign` actions, ignores per-item results, announces silence success immediately, and links investigation to a hardcoded ID. Its adapter must handle the three supported actions, status `207`, real returned IDs, and `pending_approval` wording before browser acceptance. This batch does not change the frontend or aggregate OpenAPI loader.

WAN-117 must register `NewBulk` with the existing V3 policy, the Alertmanager client, a proposal service and ledger built from the **same** environment labels and application bindings, current operations ingress sources, and the existing `LoadAlertRangeCoverage` callback. The callback must honor its two-second context deadline and perform no network I/O. With any of these missing, silence fails closed. Registration, aggregate OpenAPI loading, frontend behavior, database/runtime verification, and approval/execution wiring are separate integration work.
