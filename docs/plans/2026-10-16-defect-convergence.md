## 1. 现状

### 1.1 缺陷是怎么被发现的

10-09 至 10-12 共登记 104 条：P0 5 条、P1 22 条、P2 47 条、P3 28 条、缺能力 2 条。按每条第一次写进登记册的时间统计。验收常常干到凌晨，所以按“工作日”切分（早上 6 点前算前一天）：

| 工作日 | 新登记 | 其中 P0/P1 | 当天主要在做什么 |
| --- | --- | --- | --- |
| 10-09（到 10-10 早 6 点） | 70 | 24 | 前端第一次接真实后端：全页面对拍、黄金路径、权限矩阵、第一批故障演练 |
| 10-10（到 10-11 早 6 点） | 17 | 0 | 回滚端到端与失败演练、统一来源登记第二阶段、链路页 |
| 10-11 | 0 | 0 | 按设计图实现、D11 开发与接入 |
| 10-12 | 17 | 3（PA-88、PA-100、PA-101） | 第一次跑 D11 完整演练、第一次接真实配置仓库、nonprod 第一次收到真实告警 |

这些数字是下限：有些问题在开发中随手修掉了，没有登记。例如 10-11 GitLab 连接器激活不信任私有 CA（4e360d5），10-12 告警规则定义页遇到真实规则就崩溃（0ec6b62d，登记册里只在进展记录中提到）。

两点结论：

1. **缺陷集中出现在“第一次”**：第一次用真实数据跑完的路径，或者已有路径第一次遇到某种真实数据状态。10-12 的 3 条 P1 都是第一次跑的路径（从事件发起调查在 V3 根本没实现、返回 501；跨实例导入按应用 ID 匹配；生产端没有导入入口）。PA-70（第一次出现真实 Agent 数据，生命周期页崩溃）、PA-85（进行中的调查有 19 个时，选择器选不到最早的一个）、PA-104（第一条真实告警让告警页崩溃）则是已有路径遇到了新的数据状态。
2. **P0/P1 出现得很不均匀，短期内没有 P0/P1 说明不了问题**：10-10 也跑了不少新路径（回滚端到端、回滚失败演练），P0/P1 是 0 条；到 10-12 一跑 D11 和配置提升，又出了 3 条。所以“连续 N 天无 P0/P1”必须同时规定这些天里要用到哪些东西，否则只说明那几天没碰到。

## 2. 收敛标准

> **已被 2026-10-18 收尾方案取代**（`docs/plans/2026-10-18-release-wrap-up.md`，用户 2026-10-19 批准）：收敛目标改为 v0.1.0 公开发布，用发布门槛 G1～G6 替代下文的退出标准。原文保留备查。

### 2.1 三种标准

| 方案 | 做法 | 好处 | 问题 |
| --- | --- | --- | --- |
| A 按天数 | 连续 N 个自然日使用，没有新的 P0/P1 | 最简单，和 10-12 用户的要求一致 | 没规定每天要用到什么，空着的天、只走熟路的天也会计入 |
| B 按轮次 | 每轮执行固定清单，连续 N 轮没有新的 P0/P1 | 可以计量 | 每轮重复同一批用例，越跑越难发现新问题（测试里叫“杀虫剂悖论”：同一批用例反复跑，只能防回退，找不到新缺陷） |
| **C 覆盖门槛 + 连续轮次（推荐）** | 先让每条用户能走到的路径、每类数据状态都至少用真实数据跑过一次（覆盖门槛），然后连续 N 轮没有新的 P0/P1；每轮有固定必做内容，也有按固定顺序轮换的内容 | 直接针对 1.1 的规律：先把“第一次”的风险用掉，再看重复使用时稳不稳 | 成本最高；覆盖清单本身要先做准 |

推荐 C。理由是 1.1：缺陷来自“第一次”，不先过覆盖门槛，“连续 N 轮无 P0/P1”可能只是没碰到。

### 2.2 推荐参数

- **连续轮次 N = 5，每个自然日最多计 1 轮**。一些缺陷和时间有关，一天内连跑几轮发现不了，例如凭据到期（10-11 Kubernetes 读令牌到期后约 5 小时没人发现）、12 小时会话到期、收件箱“今天/昨天”的分组（PA-83）、7 天的链路保留边界（PA-79）。
- 可选 N = 3：阶段 2 少两轮，但把握更小。这个标准是工程上的经验门槛，不是统计证明。作为量级参考：假设每轮出 P0/P1 的概率不变、各轮相互独立，零事件时 95% 置信上限是 1 − 0.05^(1/n)，连续 5 轮无 P0/P1 只能说明这个概率大致在 45% 以下，3 轮约在 63% 以下。实际上各轮内容不同、轮与轮之间还在改代码，这两个假设都不成立，所以数字只用来说明“几轮干净证明不了多少”。真正的把握来自覆盖门槛和每轮实际执行的内容。
- **P2**：不重置计数，但退出前最后两轮新增的 P2 合计不超过 2 条；超了就继续跑，直到最近两轮满足为止。退出时没修的 P2 都要写明绕行办法。
- **上限**：从进入阶段 2 起，有效轮次累计到 N + 5 轮（N = 5 时为 10 轮）仍未达标，就停下按模块聚类复盘，由用户决定是继续、做模块级的重新设计，还是缩小 MVP 范围。这意味着第 6 轮以后再出 P0/P1，就会触发停下复盘。作废的轮次不计入上限。

### 2.3 定级与计数规则

**定级**（分级沿用验收计划，补几条示例，减少同类问题定级不一致；此前 PA-70 和 PA-104 都是页面遇到 null 整页崩溃，一个定 P1、一个定 P2）：
- 越权、数据错误（页面数字或状态与数据源不符、写错对象）：P0；
- 核心闭环（告警 → 调查 → 提案 → 批准 → 执行 → 验证 → 复盘 → Runbook）上的页面整页崩溃、白屏或整页 503：至少 P1；
- 界面上有入口，点了却是 501 或接口未注册：按缺陷定级，不算“缺能力”。只有界面不提供入口，或明确标为暂不可用时，才算缺能力；
- 宣布收敛前，审查任务复核本轮全部 P2；复核后升为 P1 的，按发现的那一轮重置计数。（**已被 2026-10-18 收尾方案取代**：改为 G1 的小范围定级复核——未修的 P2/P3 与 D63 留待复核的先例；升为 P0/P1 的发布前修掉，不重置计数。）

**计数**：
- 新出现的 P0/P1 让计数归零，包括修复引入的回归，以及“已修复”的缺陷又复现。
- 实验环境本身的问题（虚拟机时钟跳变、宿主冻结、实验组件故障）不算产品缺陷。如果因此做不完本轮必做内容，本轮作废：不计入、不重置，但要附证据（watchdog 输出、容器状态或日志）。作废轮里发现的产品 P0/P1 照样重置计数。产品在环境出问题时的表现，仍按通过标准判定（例如凭据失效后有没有明确提示）。
- 超时：宿主 1 分钟负载超过 24（本机 12 核的 2 倍）时出现的超时，要在负载低于 12 时复现一次。复现不了的，记为性能轮输入（同 D45）；能复现的，按功能缺陷定级。每轮记录排除了几次，一轮排除超过 2 次就作废。
- 回归偶发失败：同一检查立即重跑一次。重跑通过的，登记为“不稳定”（P3，查是工具问题还是产品问题）；同一检查连续两轮不稳定，就按缺陷查原因。
- AI 回答有随机性：同一问题最多重问 3 次，只要有一次编造证据或给出错误结论，就按影响定级。DeepSeek 自身的 5xx/429 是外部故障；产品要给出明确提示并能重试，否则是缺陷。
- 属于“缺能力”或“缺来源”的发现照常登记，不重置计数；如果卡住核心闭环，由用户决定要不要补。
- 已完成功能上发现的问题，一律登记后再修，不在开发中顺手修掉不记（1.1 的两个例子就是这样漏掉的），否则数字不真实。

### 4.2 阶段 1：覆盖扫荡（粗估 3～5 天，含修复）

## 5. 缺陷处理规则

- 修复时机：P0/P1 当场修；P2 在轮次之间批量修；P3 登记，收敛结束前尽量修。
- 每个修复都带一个能复现原问题的测试（Go 单元或隔离测试、验收脚本检查、Playwright 用例三选一），并加进回归。
- 按项目约定（AGENTS.md）：路由变更同步维护 `docs/api-contract.md`、`internal/apicontract/openapi.json` 和 `scripts/build-openapi.py`；数据结构变更维护 `migrations/`，迁移只在两个验收库执行，并在登记里写明是否已执行。
- 界面：只修不改外观；需要新界面元素的，先出设计图给用户审阅，同 D25、D29 的做法。
- 编号：沿用 PA 编号，从 PA-105 开始，写进新登记册 `docs/releases/<开始日期>-defect-convergence.md`；Linear 新建父任务“缺陷收敛（2026-10）”，每条一个子任务，优先级换算同 WAN-297。
- 每条缺陷多记三个字段：
  - 新颖性：首次路径 / 首次数据状态 / 首次角色 / 重复路径 / 修复引入；
  - 发现方式：回归 / 演练 / 任务卡 / 自由探索 / 用户亲测 / 审查；
  - 轮次号（阶段 0、1 记阶段）。
- 用户不在、需要做选择时：沿用此前的做法，按推荐选项决定，记为 D 条目（从 D46 起），等用户回来审阅。界面上的新元素仍然等设计图确认后再做。

## 7. 记录与度量

- 轮次记录（T3）：轮次号、日期、产物 `vcs.revision`、宿主负载（开始/结束）、凭据状态、演练场景、角色、任务卡、数据状态、探索时长、新缺陷（编号、级别、两个来源字段）、连续计数、本轮是否有效及原因、负载豁免次数。
- 每轮汇报看三个数：
  1. 新 P0/P1 条数与连续计数；
  2. 本轮第一次执行的路径与数据状态组合有多少（阶段 2 的覆盖门槛已满足，这个数反映轮换有没有真的带来新组合）；
  3. 新颖性为“重复路径”的缺陷条数。常走的路不该再出问题，这个数应当降到 0。分母太小，看绝对条数，不看占比。
- 收敛报告里画缺陷曲线：横轴为轮次（含阶段 0、1），纵轴为各级别新增条数。

## 8. 工作量、成本与风险

### 8.1 值不值得做

项目初衷是尽快交付一个可复现、可写进博客和简历的 SRE 作品。收敛的收益：
- 可以如实把“beta”换成更强的说法；
- 在真实实验环境里现场演示时不容易翻车；
- 是第 2 项性能测试的前提：在缺陷还很多的系统上做压测，大量时间会耗在功能问题上。

代价粗估 2～4 周日历时间，主要取决于缺陷数和计数被重置的次数。建议做，并用第 2.2 节的上限兜底。如果觉得太长，可以缩小覆盖范围（第 9 节第 3 项），或把 N 降到 3。

### 8.2 工作量（粗估）

| 阶段 | 估计 | 说明 |
| --- | --- | --- |
| 0 | 2～3 天 | 环境恢复与 Vault 重建约半天；T1 最不确定（按对象授权的写路由要逐条构造请求体）；T0、T2～T5 约 1 天 |
| 1 | 3～5 天 | 清单规模见 4.2；修复量不确定，是主要变数 |
| 2 | 至少 5 天（5 轮） | 每轮 2～3 小时加修复；每次重置至少多一天 |
| 3 | 约半天 | 完整回归、全部独立套件、审查、报告 |

### 8.3 成本

- 模型：只用 DeepSeek。`regress.py` 注释写黄金 API 路径一次“几美分”；以往每次演练的 AI 调查调用 6～33 次工具。用户 10-16 决定不设预算上限：每轮记录模型调用次数，异常时提醒；账单由用户在 DeepSeek 控制台查看。
- 宿主：实验三台虚拟机、观测与中间件容器、GitLab、Vault 与两个实例要连续运行 2～4 周。10-11、10-12 都出现过宿主负载高导致的超时（10-11 是用户的其他项目同时运行，10-12 即 D45），所以按第 2.3 节记录负载并归类。

### 8.4 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 宿主休眠、Docker 重启 | Vault（开发模式）数据丢失，已经发生过一次；虚拟机时钟跳变 | 收敛期间宿主不休眠（同 D1 的做法）；每轮开工核对 Vault 和 `clock-watchdog.py check`；Vault 丢失时按 4.1 第 3 步重建，本轮作废 |
| 其他 kind 集群和项目占用宿主 | 超时增多，排除和复现的成本上升 | 由用户决定收敛期间是否暂停（第 9 节） |
| 修复引入回归 | 计数反复归零 | 每个修复带测试、部署后跑完整回归；冻结功能 |
| 自动化“使用”不像真人 | 漏掉体验类问题 | 自由探索、角色轮换、用户亲测 |
| 有意无意避开高风险路径 | 收敛结论不可信 | 固定必做内容、卡池和轮换顺序；T2 实测覆盖；收敛前独立审查 |
| 测试数据越积越多 | 用例依赖的对象变化；`regress.py` 写死了 `GOLDEN_INVESTIGATION` | 阶段 0 把写死的对象改为每次查找或新建；数据积累本身算作“量大”状态的一部分 |
| 凭据中途到期 | 演练失败 | `credentials.py` 补全检查项（4.1 第 7 步），到期提醒写进轮次记录 |
| DeepSeek 不稳定、AI 回答有随机性 | 定级困难 | 按第 2.3 节的 AI 规则 |
| 发现“缺能力”后想顺手补上 | 范围膨胀 | 只登记，由用户决定，不计入收敛 |

**10-16 补充决定**（用户确认）：DeepSeek 不设预算上限，每轮记录调用次数、异常时提醒；宿主上其他 5 个 kind 集群不暂停，对拍 worker 从 6 降到 3。实测这 5 个集群合计约 6.7 GiB 内存、空闲时不到 1 个核，基线对拍时的负载主要来自对拍本身。降到 3 个 worker 后，如果连续两轮负载豁免仍超过 2 次，再考虑暂停。

**本稿的假设**：
- 宿主在 2～4 周内基本可用，可以连续运行实验环境，必要时不休眠；
