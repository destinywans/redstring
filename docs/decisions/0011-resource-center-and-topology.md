## 信息架构分工

| 区域 | 回答的问题 | 数据与边界 |
| --- | --- | --- |
| 资源中心 / 全部应用 | 有哪些应用、谁负责、部署及关联配置是什么 | 已有应用目录、负责人、团队、环境配置 |
| 资源中心 / 资源目录（规划） | 有哪些资源、归属和身份是什么 | 有来源与更新时间的资产登记/发现结果，不把连接器数量当资源数量 |
| 资源中心 / 资源关系（规划） | 部署在哪、属于谁、依赖谁 | 有来源的部署、归属、依赖关系；共享资源可以关联多个应用 |
| 基础设施 | 当前资源运行如何、发生了什么事件 | 实时或有采集时间的状态、指标、事件；复用资源身份，不复制一套资产表单 |
| 可观测性 / 调用拓扑 | 指定时间窗实际观测到哪些调用、流量和错误如何 | Trace 或其他真实调用观测；错误率与延迟需对应数据支持 |

“资源关系”覆盖服务依赖，但不等于“调用拓扑”。没有观测到流量不代表依赖不存在，登记依赖不能直接画成实时调用。两者后续共用资源身份，保留关系类型、来源、采集时间与观测窗口；仅有明确映射时互相跳转，不能用显示名称猜测。

调查画布继续表达证据、假设、上下文分支及结论；它可以引用两类视图的快照，不与资源关系混用同一语义。

## 存储方向

用户确认暂用 PostgreSQL。业务实体及关系使用结构化表，变化属性可用 JSONB；pgvector 继续处理知识/经验的语义检索，不承担精确资源关系查询。

仅当实际关系查询复杂度或经合理优化后的性能不满足需求，再评估图数据库。关系查询接口隔离存储实现，未来可以增加图查询投影或替换关系存储，不意味着把账号、审批、审计等业务全部迁离 PG。接口与关系表尚待实现，本轮没有数据库迁移或性能测试。
