# V3 evaluation case read and human label

`GET /api/v1/eval-cases/{id}` reads a registered case and its latest immutable trusted evaluator snapshot. `POST /api/v1/eval-cases/{id}/labels` records a human label for that exact snapshot. The source of the full page is `RecordEvalCaseSnapshot`, an in-process trusted evaluator API; this service does not run a model or create a score from a case registration.

## Evidence and complete response

The case registration stores `id`, `agent_id`, `title`, and `expected_ref`. Migration `138_v3_agent_eval_case_snapshots.sql` records the registration's original application/environment and introduces append-only snapshots. A trusted producer must report references for its own report, input, expected answer, candidate output, baseline output, and evaluator result. The expected reference must equal the registered reference. Candidate and baseline versions must be distinct persisted versions of the same Agent. The typed view is validated, bounded, and saved atomically with a SHA-256 payload fingerprint and management audit entry. A per-case revision, assigned while holding the case row lock, determines the latest snapshot even when concurrent submissions start in a different order. All required frontend fields (`queue`, `alert`, `evidence`, `expected`, `output`, `baseline`, `auto`) come from that exact stored view. The latest snapshot ID and fingerprint are returned with `complete_v3_dto: true`, `partial: false`, and `source_state: "trusted_snapshot"`. This service checks the persisted view, versions, scope and fingerprint; it does not independently fetch or verify the external artifacts named by the producer's references.

Registration alone returns HTTP 200 with the known case fields, `alert`, `evidence`, `expected`, `output`, `baseline`, and `auto` as `null`, `complete_v3_dto: false`, `partial: true`, and `missing`. `source_state` is `unconfigured` if the registration lacks an expected reference, otherwise `awaiting_trusted_snapshot`. The nullable response is deliberately outside the frozen frontend `EvalCase` type until a trusted snapshot exists. No page example, score, or model output is inferred from a reference.

Reads lock the case, Agent, active application/environment, session, and current grant sources, then authorize `agents.view` in that transaction. Labels require a single selected environment and `agents.change`, lock the case for update, recheck the active session and grants, and save the snapshot ID with the label and audit. A moved Agent or missing original case scope is hidden with 404. Missing trusted snapshot rejects a label with 409 `evaluation_case_not_ready`. An unavailable store/policy returns 503.

The POST contract remains `{ "next": "correct|incorrect|partial|unsure", "note": "optional" }` with `{ "next": "<submitted label>", "id": "<label id>" }`. The frozen `EvalCasePage` currently sends `{cause,evidence,safe,clarity,note,regress}` and interprets `next` as another case ID; this mismatch requires a separate product contract decision and is not silently mapped. The stored label is not an automatic evaluation result or a regression-set assignment.

The in-process producer is ready for a configured evaluator, but no evaluator or external dataset is connected in this change. That producer must redact secrets and private source content from the stored alert, evidence, and model output before submitting a snapshot; the local structural validator does not perform redaction. Migration execution, real evaluator input, authorization races, and browser behavior remain unverified because this batch requested static checks only.
