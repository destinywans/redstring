# V3 effective security policy

WAN-119 owns `GET` and `PUT /api/v1/security` and the frozen `SecurityView` in `web/src/v3/api/types.ts`. The selected environment and configured instance form one policy scope. A current human platform administrator with global `workspace.manage` and permission for that environment is required. `all` is never a valid security-policy scope.

## Source of truth

The complete response must come from a configured `RuntimeController` authority. Its snapshot must bind the exact instance and environment, carry a monotonic revision and fresh observation window, and declare that every field is complete and enforced. The controller must verify live production gates or their authoritative state, not merely echo a stored preference. Since the 2026-10-09 production acceptance (PA-05), GET without a configured controller returns `200` with all nine `SecurityView` fields `null`, `unavailable` set to `not_configured` for each, and no ETag (so PUT cannot proceed); authorization, the unresolved-operation check and the final session lock run first. A configured controller that is inaccessible, stale, partial, or untrusted still returns `503 security_authority_unavailable`. A valid snapshot is returned with an empty `unavailable` map, which PUT accepts echoed back only when empty. Do not substitute `false`, an empty array, a mock, or a local SQL row for an unknown effective state.

The current repository cannot independently prove effective SSO/SAML/SCIM, required MFA, approval passkey, session idle/IP/new-device controls, Vault availability, token lifetime, or password history. Optional TOTP enrollment is not a login enforcement policy; WebAuthn account assertion is not approval passkey enforcement; a Vault resolver or one-time probe does not establish current Vault health. A deployment must supply an audited runtime authority with reliable producers for **all** `SecurityView` fields before the complete page can be served. If any field lacks a producer, the snapshot is invalid and the configured GET is unavailable. The `enabled` and `connected` booleans are claims about actual operation, not configuration intent.

The built-in HTTPS controller posts the scope to `{baseURL}/snapshot` and an idempotent operation to `{baseURL}/apply` with a bearer credential. It requires complete JSON fields, rejects duplicate keys and non-JSON responses, limits response size and time, and does not follow redirects. The authority must persist `operation_id` before any effect, compare `expected_revision`, durably activate the requested controls, and report a new revision. The apply receipt must echo the exact `instance_id`, `environment_id`, `expected_revision`, `operation_id` and SHA-256 of the compact JSON `controls` in `controls_sha256`; a mismatched receipt is an unknown result. Repeating an ID must return the same terminal result, including after restart. HTTP 409/412 (revision conflict) and 422 (unsupported control) must guarantee **no effect** for that operation; these are the only rejected responses treated as definite failures. Every other error is an unknown outcome. An authority that cannot guarantee those semantics is unsuitable for this adapter. Every change to any `SecurityView` field or its meaning, including live SSO/Vault state, must advance the scope revision so one strong ETag always names one representation. The authority must return a fresh, complete snapshot at the receipt revision that matches every requested editable control. A receipt alone does not prove success.

## PUT boundary

The request is the full `SecurityView`. Only `scim`, `mfa_policy`, `mfa_methods[].enabled` keyed by stable ID, `approval_passkey`, `session.ip_allow`, and `session.new_device_notice` can change. SSO entries and their display/default fields, method labels/notes, session idle/max, Vault display and connection, token TTL, and password policy are read-only and must match the current authority snapshot. A control that this deployment cannot enforce must be rejected. The client must send the strong ETag from GET in `If-Match`; it binds instance, environment and revision. A missing header returns `428`; a stale revision returns `412`, while a malformed or wrong-scope tag returns `400`.

`migrations/142_v3_security_policy.sql` records each attempted operation and the last verified applied revision per scope. It is an operation ledger, not a policy enforcer. A `pending` or `unknown` operation reserves that instance/environment against another write and makes GET unavailable because a lost authority response may have applied the change. A verified readback and local success audit are required before marking an operation `applied` and returning `200`; an unverified or ambiguous outcome never returns success. Database persistence alone cannot make a requested setting effective. An interrupted request can leave `pending` before `/apply` starts, and an authority or audit failure can leave `unknown` after it may have started. Both deliberately block further reads and writes. The deployment needs an audited, operation-ID-based reconciliation procedure before enabling live writes; this repository does not yet provide an automated recovery tool.

### Resolving an unknown operation

This batch does not expose a public reconciliation endpoint. An authorized operator must inspect the ledger row and request audit, preserve its `operation_id`, `expected_revision`, scope and controls, and obtain authority-side evidence for that exact ID. If the authority's durable record says the operation applied, require its matching receipt and a fresh complete snapshot at that revision with all requested controls effective before changing the ledger to `applied` and recording a reconciliation audit. If the durable record proves rejection without effect, mark it `failed` and audit that evidence. An idempotent retry with exactly the same ID, scope, revision and controls is permitted only while the original actor still has valid authorization; apply the same receipt and readback rules. A matching snapshot or higher revision alone does not prove which operation caused it. If ID-level evidence, authorization, or complete readback is unavailable, leave the row `unknown` and the route blocked. Do not delete or clear the row just to restore availability. The deployer must supply a controlled reconciliation tool and evidence retention before enabling live writes.

## WAN-117 integration

2. The V3 entrypoint accepts `AIOPS_V3_SECURITY_AUTHORITY_URL` and `AIOPS_V3_SECURITY_AUTHORITY_TOKEN_FILE` together. The latter must name an absolute 0600 regular token file. Configure only an audited HTTPS controller that can prove the complete policy for every environment served by the instance; a partial pair fails startup, while an absent pair makes GET return the all-null `not_configured` view and leaves PUT unavailable. The endpoint and token are deployment managed and stay outside source control.

The current `SecurityPage.tsx` sends a full view without that header and therefore cannot save against this contract yet. Render `vault.connected` rather than an unconditional green “Connected” state. Remove or source the page's unverified static claims about SCIM deprovisioning time, MFA grace periods, notification channels, and credential isolation. Surface `503` and ambiguous outcomes as unavailable instead of showing mock values.
5. Verify the migrated isolated database, configured authority, exact scope and revocation behavior, real apply/readback, and browser states before claiming runtime or product acceptance. `http_test.go` (isolated PG) covers the not-configured, unauthorized, configured, failing-authority and unresolved-operation reads, and the PUT echo rule.
