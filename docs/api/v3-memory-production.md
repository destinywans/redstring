# 记忆生产与人工治理（WAN-240）

本轮补齐从新建人工资料到事实治理的正式后端链，不依赖预先 SQL 写入生产资料。这里的“生产”是**有权人类从明确发布的证据中选择准确摘录**，不是自主 AI 提炼。候选的文字是否正确仍由人确认；模型置信度、文本相似度、同步成功不构成真值或冲突证明。

## 正式流程

1. `POST /api/v1/memory/sources` 显式发布人工核准资料。
2. `POST /api/v1/memory/facts` 从指定版本产生候选。
3. 原 `POST /memory/facts/{id}/confirm|reject|expire` 确认、拒绝或过期。
4. `POST /memory/conflicts` 人工登记确有矛盾的两事实。
5. 原 `POST /memory/conflicts/resolve` 明确 keep/drop 裁决。
6. `POST /memory/sources/{id}/withdraw` 归档本轮人工发布的资料并过期仍活跃的派生事实。

全部写入仅允许单个已配置环境；`X-AIOps-Environment: all` 保持 409。新入口及原治理动作要求精确 Cookie 会话和真实人类账户。新入口要求原环境、应用与团队分别拥有 `knowledge.view` 和 `knowledge.manage`；原治理继续沿用 manage 权限且增加人类身份限制。

## 显式人工资料发布

```json
{
  "request_key": "incident-note-20261007",
  "application_id": "真实应用 ID",
  "title": "本次回滚人工复核记录",
  "body": "回滚后错误率恢复到基线。"
}
```

资料正文最多 16 KiB UTF-8，标题最多 200 字符。环境从请求上下文获得；团队从锁定的应用当前归属派生，不接受客户端任意 metadata。保存到 `knowledge_documents`，来源为 `memory://manual/<id>`，版本 1、状态 published、`origin=human_memory_source` 与 `publication=explicit_human`，同时保存内容哈希、版本快照、history 与管理审计。

`request_key` 按 **操作者 + 环境** 隔离。同 key 同资料重试返回 200/created:false；任何标题、正文、应用或团队等变化返回 409，不覆盖原资料。首次成功为 201，返回 document_id/version/content_hash 和真实范围。原 key 对已撤回资料也不能重新发布；更正资料须用新 key 明确发布，不暗中替换既有证据。

本入口不宣称外部来源已审核，不接收模型生成的自动发布权限，也不建立向量索引。已注册 Git、Confluence、Notion、Feishu、上传资料仍保留原审核与来源边界；同步成功不自动进入这里。人工发布的应用资料可由既有有权关键词知识检索读取，其已发布状态表示“人已明确提交资料”，不表示 AI 已证明内容正确。

## 精确摘录生产

```json
{
  "document_id": "发布结果的 document_id",
  "expected_version": 1,
  "expected_content_hash": "发布结果的 64 位 SHA256",
  "exact_excerpt": "回滚后错误率恢复到基线。"
}
```

来源须仍 published，版本与哈希均一致，实际正文 SHA256 与保存哈希相符，准确摘录须逐字出现在正文内。摘录最多 4000 字符，不自动裁剪/改写。来源须有完整 environment/application/team 归因；普通已有已发布资料同样可用，但来源注册记录及 V3 Runbook 不绕过各自契约混入本入口。

首次创建 candidate 并审计，201 返回 `{fact,source_content_hash,created:true,production:"human_exact_excerpt"}`。语义去重键绑定**来源文档、版本、哈希、准确摘录、环境、应用、团队**。另一有权人提交同一摘录可复用同事实；他仍须重新通过全部来源与权限检查。重复返回 200，不重复审计，也不会把已拒绝或过期事实复活。

历史迁移前的事实不强制合并或重写决定。新版去重键只约束正式生产入口创建的事实；旧服务内部方法保留兼容测试，不能以它替代正式人类授权入口。

## 冲突登记与裁决

```json
{
  "fact_a_id": "真实事实 A ID",
  "fact_b_id": "真实事实 B ID",
  "expected_revision_a": 2,
  "expected_revision_b": 1,
  "reason": "已人工核对：两段材料对同一变更是否恢复给出了相反结论。"
}
```

两侧必须处于同一精确范围、仍为 candidate/confirmed、来源版本当前有效，且分别匹配提交修订。理由是人类判断，最长 1000 字符；系统不根据文本相似度自动登记矛盾。记录规范化事实对并加审计。相同开放事实对和理由可幂等重试；理由变化、修订过期或来源撤回返回 409。真正裁决仍由原 resolve 写明 keep/drop，原子确认保留事实、拒绝另一事实并关闭冲突。

## 版本变化与撤回

读取和确认始终重新核对来源版本、范围及公开状态。普通来源更新为合法新版本后，旧事实立即不再作为当前事实可读或可确认，历史状态不被系统擅自改写。新版本可明确生产新的候选。

撤回请求提交当前 `expected_version` 与 `expected_content_hash`，仅管理 `memory://manual/` 且具有人类来源标记的文档。旧版本撤回请求返回 409，不能误伤合法的新版本。

撤回在同一事务归档资料、清空其 active_generation、把该资料至多 500 个活跃派生事实变为 expired，并写 history 与审计。拒绝事实、曾经的确认和冲突记录保留为历史；其开放冲突因事实已失效不再展示或允许裁决。不会删除原始证据或伪造赢家。已归档且无活跃事实时重试不重复审计。超过 500 个活跃事实时返回 413，先通过既有逐事实 expire 清理；新出现且本次未锁定的事实触发 409，不能漏掉后仍声称撤回完成。

## 一致性与验证边界

- 新事实与来源撤回使用来源级事务 advisory 锁串行，避免 source/fact 锁反转；冲突与原治理按事实 ID 稳定顺序锁定。
- 记忆授权在用户/会话与物理授权表锁之前取得共享 `992 → 995 → 998`，与账户、角色和矩阵撤权一致；提交前再次校验原 Cookie 未过期。
- 发布、候选、冲突、撤回及审计原子提交；审核失败或数据库写失败全部回滚。正文不抄入管理审计；冲突理由属于明确提交的治理记录。
- 请求拒绝重复键、未知字段、多 JSON 对象；机器身份不能发布来源、生产候选、确认/拒绝/过期或裁决。

新增 PG 测试在随机隔离 schema 下经过注册 HTTP、真实会话/权限/SQL，生产资料本身通过新 source HTTP 创建。验证从发布到撤回完整流程、跨环境/读权限/机器限制、版本漂移、幂等、审计失败回滚及锁等待后的会话撤销。离线单测验证输入和去重范围；未连接真实外部来源、未做前端适配、未实现后台扫描、自主 AI 提炼或自动语义冲突识别。
