# D11 交付链路：前端现状摘要

2026-10-11，给后端写 D11 设计稿作参考。基线为集成分支 `ba1b13a4`，只读代码，没有改实现。D11 范围：“变更与发布”接入 GitLab 真实数据（合并请求、流水线、部署及与告警、调查的关联）；“启用告警规则”走 GitOps（`POST /alert-rules` `mode: enabled` → 两人通行密钥批准 → 执行器提交到规则仓库 → 读回生效）。

## 1. 变更页 `/changes`

### 设计稿与示意数据展示的内容

页面代码：`web/src/v3/features/observe/ChangesPage.tsx`；示意数据：`web/src/v3/mock/domains/observe.ts` 的 `GET /changes`；类型：`ChangesView`、`Pipeline`（`web/src/v3/api/types.ts`）。

- **指标卡 4 个**：本周部署、变更失败率、前置时间 P50、变更恢复时间，各带 7 天迷你趋势。
- **来源筛选**：GitLab CI、GitHub Actions、Jenkins、Argo CD、Harbor 等来源标签，带条数，可逐个开关。
- **变更时间线**：每个服务一条泳道，部署点分成功和失败，可带版本标签（如 “v2.8.1 · 14:03”），同期告警画成色带，底部是时间轴。
- **流水线运行表**：运行号、说明、服务、阶段格（每个阶段一格状态）、状态、耗时、触发人、时间；可按“全部 / 失败 / 运行中”筛选。点一行打开详情抽屉。
- **详情抽屉**：
  - 阶段 DAG：构建、测试、扫描、预发、审批、生产，每个 job 有状态和来源图标；
  - 变更内容：路径加差异摘要；
  - 发布前风险评估卡；
  - 告警关联：“发布后 2 分钟触发 HighErrorRate · INC-1042”；
  - 三个动作：带入调查、提议回滚、在 GitLab 中打开。
- **设计稿里也没有的**：合并请求列表、提交详情、单独的部署记录列表（环境、版本、谁部署、结果）。

### 真实模式现在显示什么

- **入口**：先选服务，再从 `GET /delivery/runs`（该应用在当前环境的原生交付运行，即 Argo Workflows 运行）里选一次运行，然后才请求 `GET /changes?service_id&run_id&range=24h|7d`。这是 2026-10-09 批准的设计（`1d3b8166`）。
- **没有运行时**写“这个服务在当前环境还没有经平台执行的发布。用外部 CI 发布的版本暂时不在这里显示。”；**503 时**保留选择框，写“这次运行的证据还不完整”。
- **后端限制**：`/changes` 只认 `sources=native`（缺省也是）。只投影已持久化且成功的原生运行、经核对的 GitOps 发布事件和精确来源的事故；差异、风险、告警关联来自人工审阅记录。前端没有接 `POST /changes/{run_id}/review`。
- **选中运行后的展示**：沿用上面整套布局；详情抽屉里的三个动作在真实模式下隐藏。
- **后端已有、前端还没用的接口**：`GET /changes/records`（绑定 GitLab 项目的流水线）、`/changes/merge-requests`、`/changes/commits/{sha}`。
- **验收结论**：没有原生交付来源，所以这页记为“缺来源”（D11）。

## 3. 启用告警规则：做到哪一步

**新建规则页**（`NewRulePage.tsx`）的保存对话框有三选一：

1. 保存草稿：生成合并请求，toast 里带 `!iid` 链接；
2. 试运行 24 小时；
3. 启用：必须选一个开放的调查（与静默共用的调查选择器），提交 `POST /alert-rules` `mode: enabled` + `investigation_id`。返回 `proposal_id` 后 toast 带“查看提案”链接，然后跳回规则列表。

后端返回 503 或 501 时，“启用”选项禁用，并写“启用流程（审批与执行器）还没有接入”。

**评审页**（`ReviewPage.tsx`）：
- 回滚有专用卡片（`RollbackReviewCards`）。
- 静默和其他提案都走通用卡片：目标、差异行、执行方式、依据、恢复验证、核对清单、通行密钥批准、执行状态。
- 没有针对 `action_kind: prometheus.alert_rule.enable` 的专门展示，显示得好不好全看后端往 `target / diff / method` 里填了什么。

**执行页**（`ExecutionPage.tsx`）：
- 回滚有专用页：时间线、样本图、稳定期。
- 静默和启用规则走通用执行页：步骤、恢复观测、报告。

**规则列表**（`RulesPage.tsx`）只显示触发状态（触发中 / 待定 / 正常），不显示生命周期：草稿 MR 待合并、试运行中、启用提案待批准、执行中、已生效。新建后跳回列表，看不到刚提交的提案。

**和静默、回滚相比，启用规则缺的展示**：

| 展示 | 静默 | 回滚 | 启用告警规则 |
| --- | --- | --- | --- |
| 提议入口 | 静默抽屉 | 回滚抽屉（选修订） | 新建规则页的保存对话框（已有） |
| 评审页专用内容 | 通用卡片（匹配条件写在差异里） | 修订对比、验证计划、阻断原因 | 无：规则内容（名称、表达式、for、级别、标签、注释）、MR 链接、分支与文件路径、目标规则仓库、读回计划都要靠后端写进通用字段 |
| 执行页 | 通用执行页 + 状态文案 | 专用时间线和样本图 | 通用执行页；缺“提交 → 合并 → 读回”的步骤、MR / 提交号、Prometheus 读回结果（规则已加载、首次评估） |
| 提交后的去向 | toast 提示；静默页本地记住“已提交、等待审批”的提案 | toast 带“查看提案”链接；服务详情不显示进行中的回滚 | toast 带“查看提案”链接后跳回规则列表；列表看不到待批准或执行中的启用 |

## 4. 能直接做的，和需要新出设计图的

**按现有设计稿就能做**（前提是后端给出与 `ChangesView` 同构的数据）：

- 变更页接 GitLab 真实数据：沿用现有布局（指标、来源、泳道、流水线表、详情抽屉的 DAG、差异、风险、告警关联），只做字段映射和空、错、部分结果的状态。
- 详情抽屉的“带入调查 / 提议回滚 / 在 GitLab 中打开”在真实模式开放（设计稿里已有，示意模式在用）。
- 服务详情、收件箱、事件、对话引用里的变更链接带上具体运行或 MR（深链参数）。
- 启用规则的评审和执行先沿用通用卡片：后端把规则摘要、MR、目标路径写进 `target / diff / method` 就能看。

**需要新出设计图**：

- **变更页的选择方式**：现在是“服务 + 一次原生运行”。接 GitLab 后，是继续先选运行，还是按服务看时间范围内的全部变更？MR、流水线、部署三类对象怎么切换、怎么区分来源？
- **合并请求与提交**的列表和详情，**部署记录**列表（环境、版本、谁、何时、结果）。
- **变更与告警、调查关联的人工审阅界面**（对应 `POST /changes/{run_id}/review`）：审阅人确认差异、风险和告警关联的地方。
- **启用告警规则的专用评审卡**（规则内容、MR、目标仓库、读回计划）和**专用执行页**（提交、合并、读回生效的时间线，以及失败时的说明）。
- **规则列表的生命周期状态**，以及进入“待批准的启用提案”的入口。
- 如果后端会提供结构化的变更证据，**调查画布里的变更证据卡**也需要设计。

## 需要后端在设计稿里定下的

- 变更页的主对象是原生运行、GitLab 流水线还是 MR，三者之间的 ID 和关联字段。
- 告警、调查与变更的关联怎么来：按时间窗、人工审阅，还是两者都有；在列表里怎么标注“已审阅”和“仅时间相邻”。
- 启用规则在提案和执行记录里提供的结构化字段：规则摘要、MR、`project_id / mr_iid / branch / path`、读回状态和时间、失败原因。
- 规则列表要不要返回生命周期状态，还是由前端去关联提案。
