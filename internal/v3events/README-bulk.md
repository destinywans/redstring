# V3 alert-group bulk actions

`POST /api/v1/alert-groups/bulk` accepts a JSON object with `ids` (1–20 unique `group:` IDs, each followed by 24 lowercase hex characters) and `action` (`claim`, `investigate`, or `silence`). A write requires one selected environment. The group ID uses the same persisted environment row ID, application ID, source ID, and fingerprint as `GET /alert-groups`; it is a derived identity, not a client-supplied incident ID. The handler resolves and locks only the current members of that exact group, then applies current application or owner-team authorization.

The response preserves input order and has one result per requested ID: `{id,outcome,matched,changed,investigation_id,proposal_id,error}`. IDs and error are `null` when they do not apply. `matched` counts persisted members in a bounded, authorized group and is zero when the group is hidden, missing, or too large to count safely; `changed` counts incident rows changed and is zero for a pending silence proposal. `200` means every item succeeded. `207` means at least one item failed, so callers must inspect every result. A missing or hidden group returns `not_found`; routine group conflicts and disconnected sources appear in the corresponding item. An invalid batch, an aggregate environment, or unavailable shared storage or policy fails the request before item results.

| Action | Successful outcome | Durable effect and retry |
| --- | --- | --- |
| `claim` | `claimed`, `already_claimed` | Set the platform assignee on eligible persisted members; the same user's retry does not add another change. It does not change Alertmanager state or notification delivery. |
| `investigate` | `investigating`, `already_investigating` | Create or reuse a real investigation and root branch linked to the locked group snapshot. Return only a persisted investigation ID. Like `claim`, only members whose alert is still firing or pending count: a resolved occurrence linked to an earlier investigation no longer makes the group a `conflict` (PA-119); a group with no such member is a `conflict`. |
| `silence` | `pending_approval` when exact scope is proven | Create or reuse a pending review proposal and return its real `proposal_id` with `changed=0`. This handler does not silence alerts upstream. |

Silence uses the persisted source and fingerprint to identify the local group; those fields alone are not Alertmanager matcher labels. A successful proposal requires operator-attested configuration for a dedicated exact group identity label, with the same value in every locked member's immutable persisted labels. The attestation must establish that the label identifies only this group at the bound Alertmanager endpoint, including future alerts for the proposed duration. The proposed silence uses exact equality matchers for environment, application, and the dedicated identity. A bounded scan of the authenticated source's persisted history rejects a current sibling group with the same identity value; if that source exceeds 5000 occurrences or the scan times out, the proposal fails closed. The scan cannot prove uniqueness across other sources or future alerts, which remains an operator-attested producer invariant. Missing configuration, conflicting labels, or incomplete scope evidence yields item-level `not_connected`. `pending_approval` means that both a review proposal and immutable group evidence were stored; it is not an active silence. The proposal producer and evidence link use separate transactions, so an intervening failure can leave a proposal without evidence and return an item failure. Migration 148 prevents such a `bulk-` proposal from receiving a vote or becoming approved until matching evidence exists. The independent worker must still revalidate every bulk proposal before any execution claim. Two-person approval and that worker check are required before an upstream write.

Item failures include `not_found`, `conflict`, `not_connected`, `group_too_large`, `session_revoked`, `human_required`, and `unavailable`. Investigate also requires the current `canvas.change` grant. No direct upstream silence, infrastructure write, or external notification occurs in this handler. V3 approval and independent execution are separate paths.

The standalone contract fragment is [`scripts/v3-openapi-alert-groups-bulk.py`](../../scripts/v3-openapi-alert-groups-bulk.py). The frozen frontend currently sends unsupported `merge` and `assign` actions, ignores per-item results, announces silence success immediately, and links investigation to a hardcoded ID. Its adapter must handle the three supported actions, status `207`, real returned IDs, and `pending_approval` wording before browser acceptance. This batch does not change the frontend or aggregate OpenAPI loader.

The V3 composition root registers `NewBulk` with the existing V3 policy and injects `BulkSilenceSource` only when the ordinary silence executor and an additional reviewed private group binding are configured. It calls `CreateReady` after releasing the group transaction and before creating a proposal. Approval options and votes call `BulkEvidenceReadyWithTx` after loading the locked, verified action; it checks immutable evidence, the active reservation, and the bounded current source snapshot without taking group or catalog locks. In the independent worker's execution-claim transaction, `PrelockBulkSilenceWithTx` runs **before** locking the Alertmanager catalog target, and `RevalidateBulkSilenceWithTx` runs after the verified approved action and current grant locks but before reserve/claim. Missing, released, or stale evidence fails closed. Migration 150 keeps the migration 148 approval guard but moves its permanent group and endpoint/identity uniqueness into active reservation rows. A new authorized bulk request may release a prior reservation only after the proposal was rejected, or its attestation actually expired while still pending, and only if there has never been an approval decision, execution claim, or silence-create operation for the original action. The immutable evidence, one-way release record, and audit event remain. A released predecessor's ID forms the next stable idempotency generation, so retries of the new proposal reuse it while another rejected or expired proposal can be submitted from freshly checked group evidence. An approved, claimed, possibly sent, or uncertain operation retains its reservation even if later marked expired. A pending proposal whose reservation was released after attestation expiry still reads as `pending` in generic proposal details; the released reservation is the domain closure record and it cannot receive further bulk approval or execution. Apply migrations 146, 148, and 150 before enabling this configuration. The operator must provide a reviewed per-environment/source/application binding with a dedicated label name, config revision and attestation digest, expiry, and the current Alertmanager endpoint binding fingerprint. The aggregate OpenAPI and main contract describe this conditional backend path; database/runtime and frontend behavior still require separate verification.
