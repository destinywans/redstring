# V3 inhibition rules, preview, and drafts

`GET /inhibitions` reads the current environment-bound Alertmanager `/api/v2/status` configuration. It retains the existing exact environment/application visibility rules. Matcher values are now redacted in the response; the server classifies with the original values before redaction. The endpoint returns `206 partial` with `active: null` and `hits_7d: null` for every visible rule because Alertmanager status does not provide either fact. `config_revisions` contains the SHA-256 digest of each observed `config.original`; for one environment the digest is also a quoted ETag. Neither the digest nor the response includes receiver secrets.

`POST /inhibitions/preview` accepts `application_id`, `source`, `target`, and `equal`. Every matcher has `k`, `op`, and `v`. The caller must select exactly one environment and have environment-wide `silences.view` and `silences.manage`; the application must have an explicit server-owned provider-label binding and current ownership. The server adds exact environment and application matchers to **both** sides. User matchers cannot override them. Target severity must be an exact `P2`, `P3`, or `P4`, or a literal `=~` list such as `P2|P3|P4`; no negative, broad, or P1 target is accepted. This finite raw-label contract must be validated again by a future publisher against its actual severity mapping before activation.

The preview requires a trusted, read-only `InhibitionHistorySource` attesting complete firing-interval occurrence coverage for `[now-7d, now]`. `InhibitionHistoryClient` is a configurable HTTPS/loopback read adapter for `GET /api/v1/inhibition-history?from=...&through=...`. Its bounded response has `environment_id`, configured `source_id`, `complete`, `coverage_start`, `coverage_end`, and at most 500 `alerts` with unique `id`, `labels`, `starts_at`, nullable `ends_at`, and `firing_interval: true`. The endpoint rejects missing configuration with `501 not_connected`; failed or incomplete coverage returns `503` without a count. A live `/api/v2/alerts` snapshot and local webhook incidents alone cannot establish this seven-day coverage. Successful `potentially_suppressed` counts distinct target occurrences with an overlapping source firing interval and equal label values; it is a simulation, while `actual_inhibition_hits` stays null. The sample contains at most ten distinct real `alertname` values from matching targets. No writes occur.

`POST /inhibitions` uses the same input and additionally requires the quoted GET ETag in `If-Match` and an `Idempotency-Key`. It checks the current config revision from one status read, then records an immutable, scoped JSON proposal and audited export attempt in `v3_inhibition_drafts`. A configured `InhibitionRepository` opens an MR containing `ops-config/inhibitions/<draft-id>.json` in the existing GitOps project, with a source branch prefix disjoint from route drafts and config-sync promotions and a target different from config-sync's target. The response is `202 pending_review` with a verified open MR identity. This is local submission evidence; the current MR and runtime states are null. Same-key retries reconcile the same branch, path, and payload, including an uncertain prior export. The endpoint never merges the MR, applies or reloads Alertmanager, or sends a notification. A config owner must validate the revision, P1 mapping, conflict semantics, and manual promotion separately.

The V3 startup loads an optional history source from `AIOPS_V3_INHIBITION_HISTORY_CONFIG`. The 0600 JSON file binds each configured instance environment to a unique `source_id` already present in the validated Alertmanager webhook policy, with `url`, optional `bearer_token_file`, and `allow_http` (nonproduction only). Each configured environment must have exactly that one validated webhook source: the current history protocol attests one stream and cannot prove coverage across multiple streams. Production requires HTTPS. Without a configured, complete seven-day history source, preview returns `501 not_connected` or `503` rather than a fabricated count. The configured source must still be checked for real coverage before operational use.

The V3 startup also loads the optional GitLab review repository from `AIOPS_V3_INHIBITION_TARGET_BRANCH` and `AIOPS_V3_INHIBITION_BRANCH_PREFIX`. Both must be set together and remain distinct from config promotions and notification route drafts; otherwise startup fails. The repository reuses the reviewed GitLab project and credentials but applies its own `aiops-inhibition-draft` MR label. The draft export holds current authorization, session, and exact attempt locks through a bounded 30-second GitLab call; a session with under 31 seconds remaining is rejected before that call. A failure before any remote attempt releases its lease and audits the result; an attempted but uncertain export stays reconcilable. Migration `139_v3_inhibition_drafts.sql` is wired but has not been run against the existing database. The config owner must confirm that no external automation merges or activates MRs on the inhibition review target before enabling writes.

The aggregate OpenAPI includes `scripts/v3-openapi-inhibitions.py`. The frozen frontend expects raw matcher values, sends no `application_id`, ETag, or idempotency key, and presents save as immediate activation; it cannot yet use this contract. Static compilation and contract checks do not prove live historical coverage or GitLab export.
