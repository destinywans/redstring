# WAN-118: product silence proposals

`POST /api/v1/silences` and `DELETE /api/v1/silences/{id}` in `internal/v3alertmanager.Service` submit immutable human-review proposals. They never call `Client.CreateSilence`, `Client.ExpireSilence`, or `DatabaseSilenceLedger.ReserveCreate`. The response is `202 pending_review` with a proposal ID and action digest, `effect=no_upstream_write`, and null upstream/execution fields. The composition is opt-in: with the execution flag unset, either route returns `501 not_connected` before recording a proposal. With the flag set, the strict private source, proposal-bound Passkey service, approval tables and independently polling worker must be ready; loss of a configured dependency fails closed.

The independent machine contract is `scripts/v3-openapi-silence-product.py`, now included by `scripts/v3-openapi.py` in the aggregate OpenAPI. The frozen V3 frontend currently sends `duration` and does not send `investigation_id` or `Idempotency-Key`; it must be adapted before page acceptance. No frontend edit is part of this batch.

A deployment must explicitly set `AIOPS_V3_SILENCE_EXECUTION_ENABLED=true`, enable proposal-bound passkeys, and supply the private HTTPS Alertmanager source. The source file must be absolute, regular and mode `0600`; each configured endpoint requires a mode `0600` token file and verified webhook source/application bindings. This setup does not prove the external Alertmanager is healthy or that any silence was executed.

## Submission contract

Both requests need the selected exact `X-AIOps-Environment` scope, a live human cookie session, a unique `Idempotency-Key` of 8–128 characters, an open investigation mapped to the exact active application and environment, and current `silences.manage` plus `proposals.change`. The selected environment cannot be `all`. The server verifies those conditions in the proposal transaction and locks the session, user, catalog and grant sources through commit. Matching idempotent retries return the same still-pending proposal; a changed request or non-pending proposal is a conflict.

`POST /silences` takes `investigation_id`, 1–20 `{name,op,value}` matchers, `duration_seconds` from 1800 to 86400, and a nonempty `comment`. Exactly one `application = <bound label>` matcher is required. The server adds and verifies an exact environment matcher and fingerprints its configured Alertmanager binding. `v3proposals.SilenceProductProducer` reuses `CreateSilenceProposalForSession`; the action and readable review content are digest-bound and audited in one transaction. It creates no upstream operation reservation. The proposal is a request for later human approval, not approval itself. Request text limits are UTF-8 bytes: 128 for the investigation ID, 256 per matcher value, and 1000 for the comment or cancellation reason.

`DELETE /silences/{id}` takes a UUID upstream ID plus `investigation_id` and nonempty `reason`. It requires a locally confirmed create operation whose ID, upstream ID, payload, environment, application and owner team still agree. A fresh complete Alertmanager read must show exactly one matching UUID and operation annotation, unchanged full payload, active or pending time window, and exact environment and application scope. The configured endpoint fingerprint is included in the action. `DatabaseSilenceCancelProduct` and `SilenceProductProducer.WritePendingSilenceCancelWithTx` commit the immutable intent, proposal action, review content and audit atomically. An arbitrary upstream ID cannot be used to cancel a silence.

Review content language and wording (PA-121): the readable review of both proposals is written once, in the requester's language (`Accept-Language` starting with `en` gives English, anything else Simplified Chinese; `httpapi.EnglishRequested` reads it from the authenticated request context), and is digest-bound as before. Reviewers see the requester's language. The text describes the current flow: two approvers other than the requester approve with a passkey; after the second approval the independent executor rechecks and writes the silence (or expires it) once, never retries, and reconciles an unknown outcome only by reading Alertmanager. Proposals written before PA-121 keep their English review ("No silence is created by this proposal" and similar); the loaders used by approval and the executor accept exactly the Chinese, English or that earlier English review for the stored action, so those proposals still load. Stored reviews are never rewritten.

## WAN-117 composition and limits

1. `cmd/aiops` now shares one trusted Alertmanager client, ledger, proposal service and server-owned environment/application bindings across create/cancel producers and the executor. The HTTP handlers use the selected V3 scope and current cookie; producers recheck authority inside the database transaction.
2. `Service.SilenceWorkflow` is supplied only behind the explicit opt-in. `CreateReady` and `CancelReady` check the selected environment, proposal action source, durable approval authority, running worker and claim table on each request. Startup registration alone does not imply readiness.
3. Approval options issue a five-minute proposal/action/review-bound WebAuthn challenge. A first distinct eligible human vote returns `202 pending_review`; the second returns `200 approved` with a durable `execution_id` handoff. The HTTP approval handler never writes to Alertmanager.
4. The worker consumes only durable approved decisions. The executor verifies the immutable action, current grants and approval proof in the claim transaction before any upstream create/cancel. An uncertain dispatch is read-only reconciled; a second same-key request must not trigger another write.
5. Migrations 140, 141 and 145, real Passkey/Alertmanager behavior, process recovery, frontend requests and user-visible page states have not been exercised in this integration batch. The three main routes are marked implemented only for their conditional backend code paths.

`migrations/140_v3_silence_cancel_intents.sql` extends the proposal action-kind constraint and adds the immutable cancellation intent. Applying that migration does not enable cancellation by itself.
