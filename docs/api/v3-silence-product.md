# WAN-118: product silence proposals

This batch registers `POST /api/v1/silences` and `DELETE /api/v1/silences/{id}` in `internal/v3alertmanager.Service`. The methods submit an immutable human-review proposal. They never call `Client.CreateSilence`, `Client.ExpireSilence`, or `DatabaseSilenceLedger.ReserveCreate`. The response is `202 pending_review` with a proposal ID and action digest, `effect=no_upstream_write`, and null upstream/execution fields. If approval or the independent executor is not configured, both routes return `501 not_connected` before recording a proposal. The partial wire-up in this branch therefore does not make either product action available at runtime.

The independent machine contract is `scripts/v3-openapi-silence-product.py`. WAN-117 owns its inclusion in `scripts/v3-openapi.py`, the generated OpenAPI, and the primary V3 contract. The frozen V3 frontend currently sends `duration` and does not send `investigation_id` or `Idempotency-Key`; it must be adapted before page acceptance. No frontend edit is part of this batch.

## Submission contract

Both requests need the selected exact `X-AIOps-Environment` scope, a live human cookie session, a unique `Idempotency-Key` of 8–128 characters, an open investigation mapped to the exact active application and environment, and current `silences.manage` plus `proposals.change`. The selected environment cannot be `all`. The server verifies those conditions in the proposal transaction and locks the session, user, catalog and grant sources through commit. Matching idempotent retries return the same still-pending proposal; a changed request or non-pending proposal is a conflict.

`POST /silences` takes `investigation_id`, 1–20 `{name,op,value}` matchers, `duration_seconds` from 1800 to 86400, and a nonempty `comment`. Exactly one `application = <bound label>` matcher is required. The server adds and verifies an exact environment matcher and fingerprints its configured Alertmanager binding. `v3proposals.SilenceProductProducer` reuses `CreateSilenceProposalForSession`; the action and readable review content are digest-bound and audited in one transaction. It creates no upstream operation reservation. The proposal is a request for later human approval, not approval itself. Request text limits are UTF-8 bytes: 128 for the investigation ID, 256 per matcher value, and 1000 for the comment or cancellation reason.

`DELETE /silences/{id}` takes a UUID upstream ID plus `investigation_id` and nonempty `reason`. It requires a locally confirmed create operation whose ID, upstream ID, payload, environment, application and owner team still agree. A fresh complete Alertmanager read must show exactly one matching UUID and operation annotation, unchanged full payload, active or pending time window, and exact environment and application scope. The configured endpoint fingerprint is included in the action. `DatabaseSilenceCancelProduct` and `SilenceProductProducer.WritePendingSilenceCancelWithTx` commit the immutable intent, proposal action, review content and audit atomically. An arbitrary upstream ID cannot be used to cancel a silence.

## WAN-117 integration points

1. Construct one trusted `*v3alertmanager.Client`, `*DatabaseSilenceLedger`, `v3proposals.Service`, `v3proposals.SilenceProductProducer`, and `DatabaseSilenceCancelProduct` with the same database and server-owned environment/application bindings. Set `Service.Source` to that client, `SilenceCreateProposals` to the producer, and `SilenceCancelProposals` to the cancellation product. The HTTP handlers use the selected V3 scope and current cookie; the producers recheck authority inside the database transaction.
2. Supply `Service.SilenceWorkflow` only when `CreateReady` and `CancelReady` can attest, for that selected environment, a durable independent human approval gate and an executable worker for the respective action. A proposal producer or Alertmanager client alone is insufficient. Until then, leave the workflow absent so the route returns `501 not_connected`.
3. For create approval, load and verify the immutable action and review digests, require the configured human/passkey approval policy and current authority, then separately reserve via `DatabaseSilenceLedger.ReserveCreate` and dispatch through the independent worker. Preserve the existing dispatch/unknown/reconciliation state machine and do not retry ambiguous sends blindly.
4. For cancellation approval, load the exact proposal and `v3_silence_cancel_intents` row, verify the stored action/review digests, approved human decision and current grants, connector fingerprint, create operation and a fresh complete upstream observation. Persist a one-shot execution claim before `Client.ExpireSilence`, audit the attempt/result, and treat an ambiguous response or proxy 404 as unresolved until observation proves expiry. A second same-key request must never trigger a second dispatch. The execution claim, status and approval tables belong to WAN-117; this batch only records pending intent.
5. Integrate this fragment into the aggregate OpenAPI and primary contract after the approval/executor state machine is implemented; then adapt the frozen frontend request DTOs and verify isolated PostgreSQL, actual HTTP and environment-bound Alertmanager behavior. This batch ran no migrations, PostgreSQL tests, Docker or external writes.

`migrations/140_v3_silence_cancel_intents.sql` extends the proposal action-kind constraint and adds the immutable cancellation intent. Applying that migration does not enable cancellation by itself.
