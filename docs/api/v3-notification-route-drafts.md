# V3 notification route drafts

`GET /notification-routes` reads the current Alertmanager `/api/v2/status` configuration for one selected environment. It only returns the subtree selected by a single exact environment matcher directly under the global root. If earlier siblings could also match that environment, or the branch continues into later siblings, it returns an error. The response is a structural projection: matcher values and receiver names are redacted, receiver targets and credentials are excluded, and `config_revision` is the SHA-256 digest of the exact observed `config.original`. The same revision is returned as the quoted ETag.

`POST /notification-routes/test` evaluates one bound sample label set against that same scoped tree and returns matching node-ID paths, opaque receiver refs and inherited timing. It does not send a notification. Time-conditional routing cannot be reported as an active path without Alertmanager's live interval decision, so it fails closed.

`POST /notification-routes` requires an exact `If-Match` ETag, an `Idempotency-Key`, an active bound application, environment-wide `alert_rules.view` and `alert_rules.manage`, and an existing receiver ref from the observed tree. It records a draft and audited export attempt in `v3_notification_route_drafts`, then creates an open GitLab MR containing `ops-config/notification-routes/<draft-id>.json`. The draft includes the source revision, exact environment and application matchers, additional matchers, grouping/timing and an opaque receiver ref. It marks sibling insertion order for manual review. The endpoint neither merges the MR nor changes running Alertmanager.

Receiver refs use `environment_tree_unique_preorder_v1`: starting at the projected environment root, walk nodes depth first in child order and assign `receiver-1`, `receiver-2`, ... to each distinct effective receiver name on first encounter. Inherited uses of the same name keep the same ref. A future activation adapter must read the exact source revision, resolve the ref there, review sibling order and conflicts, then separately publish and observe the effective configuration. If that revision is gone or changed, the draft requires a new review; never resolve the same ref against another revision.

The route GitLab client uses the existing GitOps project's endpoint, project ID and credential, but a branch prefix and **target branch distinct from V3 config-sync promotions**. Set both `AIOPS_V3_NOTIFICATION_ROUTE_TARGET_BRANCH` and `AIOPS_V3_NOTIFICATION_ROUTE_BRANCH_PREFIX` to server-owned names; omit both to keep POST unavailable. A partial or overlapping configuration fails startup. Route MRs use the separate `aiops-notification-route-draft` label rather than `aiops-config-promotion`. Config-sync lists merged MRs for its target branch before filtering the source prefix, so a shared target branch can starve its bounded list. The target branch, prefix and label are three separate boundaries; none makes the draft active. This path also requires the configured promotion repository and migration `138_v3_notification_route_drafts.sql`, which has not been run in the existing database.

The remote export is bounded to 30 seconds total. During it, the service holds the current application, Cookie session, grant sources and exact draft attempt locks so an explicit revoke or logout commits before the export or waits for it. A Cookie with less than 31 seconds left is refused before the write. If the preflight fails before any GitLab request, the service atomically releases that attempt's lease and audits the non-export so a new session can retry the same key; if cleanup cannot be confirmed, it returns 503. Uncertain remote results remain in the idempotency ledger for the same-key retry. Holding those locks can delay concurrent role edits for at most the bounded export and rollback cleanup; real GitLab and database concurrency have not been exercised in this integration batch.

`pending_review` is the local submission status. An idempotent replay returns the recorded MR identity; it does not query the current MR state. The response leaves current MR and runtime state null. No current route activation or delivery is implied by an MR, a merged MR, or a successful draft export.
